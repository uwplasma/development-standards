# Scientific evidence

**Start with the claim.** Write down the governing equation or numerical contract, conventions, units, hardware budget, quantities of interest and operating regime. Search papers, preprints, technical reports, upstream documentation and competing implementations on GitHub and GitLab. Follow citations to the original method. Record a revision or DOI and the particular equation, source routine or limitation that informs the change. If a result disagrees, check definitions, normalization, boundary conditions and discretization before changing a sign or tolerance.

**Choose an independent reference.** For a new solver compare with an analytic or manufactured solution and, where available, a trusted independent code. For sparse solves consider PETSc/KSP, MUMPS and SuperLU_DIST. For transformations and orbit calculations use codes that implement the same coordinates and assumptions. Check more than one code when a convention or comparison is uncertain. Clone or install appropriate references in isolated environments and record the version. Keep heavyweight references optional. Document license and credit before reusing code. A citation alone cannot establish agreement.

**Measure the baseline first.** Run an actual simulation, example and relevant tests on the base and candidate. Fix the hardware, device count, thread count, dtype, tolerances, input, shapes and software stack. Include the JAX, jaxlib and accelerator versions. Record cold compilation, warm synchronized execution and peak host/device memory separately. Warm up first, use repeated trials, alternate revisions when possible and report the spread. A faster kernel warrants an application-level check. Keep profiles and traces as artifacts. [JAX benchmarking](https://docs.jax.dev/en/latest/benchmarking.html)

**Test the science.** Use conservation, symmetry, dimensions, sign, order of convergence, stability or an independently computed residual, as appropriate. Cover a normal case, a known limit and a failure mode, including a near-singular or under-resolved case where relevant. Compare at matched accuracy. For example, the Eisenstat–Walker criterion constrains the inner residual. Validate the forcing sequence against the paper. Measure iteration savings separately on a workload where savings are reproducible. [Original paper](https://doi.org/10.1137/0917003) · [UWPlasma application](https://github.com/uwplasma/SOLVAX/pull/213)

**Verify the derivative users need.** Exercise the public map from physical inputs through the solve to an observable or objective. Check a directional derivative with a Taylor or finite-difference step sweep and, for a new linearization, verify the JVP/VJP adjoint identity. Include complex transpose conventions, restart behavior, tolerances and nonsmooth points where relevant. Keep host I/O outside transformations. If a native solver is introduced, define and test its derivative rule and a portable path. [SOLVAX example](https://github.com/uwplasma/SOLVAX/blob/main/examples/06_implicit_differentiation.py)

**Use profiling to choose the implementation.** Separate compilation, transfers, allocation, factorization, solve and communication. Consider factor reuse, a preconditioner, different time stepper or optimizer before adding a kernel. Try CPU threading, batching or multi-device sharding when the profile supports them. For a GPU bottleneck, compare a Pallas implementation with the existing JAX/XLA path at realistic sizes, including backward time and memory. Retain the portable CPU implementation and document the supported devices and precision. Put reusable numerical algorithms in SOLVAX. Keep geometry, physical models and observables in the physics code. Measure a downstream application before recommending a dependency floor or release.
