# Public interfaces and CI

**Examples teach one calculation.** Start with a short docstring stating the question, units and expected result. Put editable inputs at the top, run the simulation, then print the scientific result and save or plot only useful outputs. Print an immediate start message for long calculations and a bounded progress update at meaningful intervals. Keep scripts self-contained and runnable from a clean installation. Use a flat example script without argument parsing or a main() wrapper. A short named function is appropriate for an objective passed to grad. Implement configuration parsing once in the installed CLI.

**Python and TOML share the same model.** Public simulation options should be accessible from Python and from the installed CLI using a documented TOML input. Exercise both with a small physical case and compare observables, units and defaults within the stated tolerance. Keep backward compatibility, deliberate docstrings and clear errors. SOLVAX's low-level linear operators can be tested through a calling physics application. [DKX tutorial input](https://github.com/uwplasma/DKX/blob/main/examples/tutorials/02_cli_case.toml)

**Keep the repository small.** Include files that someone needs to run, test or understand the change. Write generated arrays, traces, tables and simulation output to artifacts. Compress figures and movies and inspect their rendered quality. Reference machine-held equilibria by stable identifier. A small reviewed schema, hand-authored input or independent reference table can be necessary. Explain its purpose and provenance. Keep installed dependencies lean, with optional accelerator and comparison tools.

**Coverage and scientific validity have separate tests.** Target at least 95% coverage for each supported package and changed executable code, subject to the owner's definition of the metric. Preserve any stricter line or branch gate. Report uncovered behavior by module so a large well-tested module cannot hide a missing scientific path. Retain unit and regression tests alongside literature-based, numerical and physics checks. Report real deficits. Changing the denominator, tolerances, exclusions or hardware to pass a gate needs a separate scientific or implementation justification and owner review.

**Use CI capacity deliberately.** Run the cheap structural check and the affected scientific witness on PRs. Reuse existing test jobs and combine coverage data from the exact revision. Run complete matrices, expensive parity cases, scaling and reference-code comparisons on scheduled or owner-triggered jobs. A change depending on one of those results needs that result on the candidate before merge. Cancel superseded work. Keep secrets and untrusted PR execution off persistent local machines. Use RUNNER_TEMP for job-created Python environments, point install and execution at the same interpreter, and upload only the artifacts needed to interpret a result. Keep hardware-specific failures visible.
